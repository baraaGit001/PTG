# 2026-09-04-2

First actual boot of `apps/api`. It had never been run — the browser was
getting `ERR_CONNECTION_REFUSED` on `localhost:3001` because nothing was
listening, and four separate bugs sat between that and a working server.

## Did

- **Build cache vs. `deleteOutDir`** — `nest-cli.json` sets
  `deleteOutDir: true`, which wipes `dist/` but not `tsconfig.tsbuildinfo`.
  Incremental `tsc` trusted the cache, reported "Found 0 errors", emitted
  nothing, and `nest start` then spawned a `dist/main.js` that was never
  written. Isolated it to this pair by building twice with and without the
  buildinfo present. Fixed by moving the cache inside `outDir` via
  `tsBuildInfoFile` in [apps/api/tsconfig.json](../../apps/api/tsconfig.json),
  so `deleteOutDir` clears both together.
- **Unbuilt workspace packages** — `@ptg/config`/`@ptg/types` resolved to `.ts`
  sources that plain `node` can't load. See
  [[../Decisions/0003-internal-packages-ship-compiled-output]].
- **Type-only imports broke all DI and validation** — 128 imports across 52
  files. See [[../Decisions/0004-no-type-only-imports-for-injectables]].
- **`JwtService` unavailable to the global guard** — `JwtAuthGuard` is bound
  app-wide via `APP_GUARD` in `AppModule`, but `JwtModule.registerAsync` lived
  inside `AuthModule` and wasn't exported, so it couldn't resolve outside that
  module's context. Added `global: true` to the registration, matching how
  `RedisModule`/`RbacModule` already share app-wide infra.

Verified: the three requests that were failing in the browser
(`/settings/public`, `/categories`, `/products?page=1&pageSize=20&sortBy=newest`)
all return 200 with seeded data, CORS preflight from `localhost:5173` returns
204, `pnpm dev:api` watch mode boots clean, and `pnpm typecheck` passes across
all 8 projects.

## Also fixed (production image)

Building the image surfaced three more failures, none of which had ever been
exercised. `docker build` now succeeds and the container serves real data.

- **pnpm could not run at all.** All three Dockerfiles and CI pinned Node 20,
  but `packageManager: pnpm@11.5.2` requires `node:sqlite`, which only exists
  in Node 22+ — `pnpm install` died with `ERR_UNKNOWN_BUILTIN_MODULE`. Bumped
  the three Dockerfiles, `.github/workflows/ci.yml`, and `engines` to Node 22,
  matching the 22.18 already used locally.
- **The runtime stage flattened pnpm's symlink farm.** It copied
  `node_modules` into `/app` without ever copying `/repo/packages`, so the
  links for `@ptg/config`/`@ptg/types` pointed at paths absent from the image,
  and the `/repo/apps/api/*` → `/app/*` move broke the relative links anyway.
  The runtime now reproduces the `/repo` layout the install was made in.
- **Prisma loaded the wrong query engine.** With no `openssl` in the image the
  version probe failed, Prisma defaulted to an openssl-1.1.x engine, and
  loading it against Alpine's openssl 3 died on `libssl.so.1.1: not found`.
  Added `apk add --no-cache openssl` to the base and runtime stages.
- Added a root `.dockerignore`. The build context had none, so the host's
  Windows `node_modules` — including native `argon2` and Prisma engine binaries
  — were being copied over the Linux ones installed inside the image.

## Open questions / follow-ups

- `pnpm dev` starts all three apps in one pnpm job on Windows; killing the
  parent takes the Vite servers down with it. Worth knowing before force-killing
  anything in this repo.
- Hit a transient `Can't reach database server at localhost:5432` while Postgres
  was up and healthy. Docker Desktop publishes 5432 on both `0.0.0.0` (its
  proxy) and `[::1]` (`wslrelay.exe`), Windows resolves `localhost` to `::1`
  first, and the relay briefly stopped forwarding. It recovered on its own. If
  it recurs, point `DATABASE_URL` at `127.0.0.1` instead of `localhost` to stay
  on the IPv4 path, or restart Docker Desktop.
- Only the API image was built and run. `apps/web` and `apps/admin` got the same
  Node 22 bump but their images were not built, and neither was the full
  `docker compose -f docker-compose.yml -f docker-compose.prod.yml` stack.
- The API image still ships the full workspace `node_modules` (dev dependencies
  included) rather than a pruned production install. It works, but the image is
  much larger than it needs to be.
