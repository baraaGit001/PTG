# 2026-09-04-3

Chased a blank page in the browser. The dev server was innocent — the cause
was Internet Download Manager on this machine — but two real repo bugs
surfaced on the way, one of them a broken `pnpm build`.

## Did

### The reported symptom

`http://localhost:5176` rendered nothing, console full of

```
Failed to load module script: Expected a JavaScript-or-Wasm module script
but the server responded with a MIME type of "".
```

Narrowing it down:

- `curl` against the same dev server returned `200 text/javascript` for every
  module in the graph — 139 of them on web, 119 on admin. A crawl of the
  whole graph over HTTP found nothing wrong.
- Driving a real Chromium at it reproduced the failure immediately. Every
  `.tsx` URL returned `200`; every `.ts` URL returned **`204 No Content`,
  no `Content-Type`** — `/src/lib/api-client.ts`, `/src/i18n/index.ts`,
  `packages/ui/src/index.ts`, and so on. A module with no MIME type is
  refused, so `App.tsx` loaded but nothing it imported did.
- The 204's headers (`connection: close`, `pragma: no-cache`, no `Date`)
  were not Node's. Pointing the same browser at a bare six-line
  `http.createServer` on another port reproduced it there too, and **the
  server never logged the request** — it was answered inside the browser.
- Characterising the rule: `.ts` and `.exe` are blocked (case-insensitively);
  `.tsx`, `.mts`, `.cts`, `.js`, `.mjs`, `.mp4`, `.m3u8`, `.dll`, `.php` are
  not; any query string (`?x=1`) bypasses it.

Widening the probe gave the full blocked set: `ts exe zip rar 7z mp3 pdf apk
msi bat cmd com iso docx m3u avi mkv tar gz bin img wav doc` — blocked;
`tsx mts cts js mjs tsv txt json css htm mp4` — not. Every blocked extension
is in `HKCU\Software\DownloadManager\Extensions`, Internet Download
Manager's "grab automatically" list, which contains `TS` because `.ts` is
also an MPEG transport stream. (`mp4` is in IDM's list but passes — the one
unexplained entry.)

The mechanism is **`IDMWFP` (`idmwfp.sys`), a Windows Filtering Platform
driver**, `Auto` start, running. Not the browser extension — which is why a
freshly-downloaded Playwright Chromium with an empty profile was affected
while `curl` was not.

Three things that look like they should fix it and do not:

- Adding `localhost`/`127.0.0.1` to IDM's `ExceptionServers`. That list gates
  auto-download prompts, not the driver's grab.
- Removing `TS` from `Extensions` and restarting `IDMan.exe`.
- Removing `TS` **and** reloading the driver (`sc stop`/`sc start`) with IDM
  restarted afterwards so it could push the new list. Still blocked — the
  driver does not source its list from that registry value.

What worked: **`sc.exe stop IDMWFP`** (elevated). `.ts` went from a synthetic
`204` to a real `200` that reaches the server, immediately, with IDM running.
`.exe` stays blocked by something else in Chromium, which does not matter
here. Then `sc.exe config IDMWFP start= demand` so it does not return at
boot. Reverting is `sc.exe config IDMWFP start= auto` + reboot.

IDM's own settings were put back byte-for-byte — the only change on the
machine is the driver's start type. The cost is IDM's "advanced browser
integration"; the IDM extension is installed in Brave and Chrome already, so
downloads still get grabbed there.

### `pnpm build` was broken (real bug)

`vite build` died on `"DEFAULT_LOCALE" is not exported by
"packages/types/dist/index.js"`. [[../Decisions/0003-internal-packages-ship-compiled-output]]
made the internal packages emit CommonJS; tsc lowers the `export *` barrel to
`__exportStar(require(...))`, and Rollup cannot resolve named imports through
that. Dev worked because Vite's dep optimiser converts CJS at runtime, so
this had been broken and invisible since 0003 — the frontends had not been
rebuilt since. Fixed with a dual ESM + CJS build:
[[../Decisions/0006-internal-packages-ship-dual-esm-cjs]].

### Four dev servers at once (real bug)

Ports 5173–5176 were all listening: two copies of web, two of admin, from
`pnpm dev` having been started more than once. Neither Vite config set
`strictPort`, so each new run silently took the next free port — and two
servers for the *same* app share `apps/<app>/node_modules/.vite/deps` and
overwrite each other's optimised bundles. That is a second, independent way
to get modules that fail to load, and it is why the browser was on `:5176`
at all. Both configs now set `strictPort: true`, so a duplicate run fails
with "Port 5173 is already in use" instead.

### Smaller things

- Added `favicon.svg` to both apps and linked it from `index.html` — that
  was the other console line in the report (`/favicon.ico` 404). Web is
  emerald, admin darker, so the two tabs are tellable apart.
- `resolve.dedupe: ['react', 'react-dom']` in both configs. `@ptg/ui` is
  source-linked and carries its own react devDependency, so a second copy
  of React can otherwise reach the graph.
- Dropped `charts: ['recharts']` from **web**'s `manualChunks`. Nothing in
  `apps/web` imports recharts (only admin's dashboard does), so the entry
  was forcing an unused 370 kB chunk into the build. Admin keeps it.

- `pnpm test` — 45 passing (33 API/Jest, 9 web, 3 admin/Vitest).
- `pnpm build` — passes for the first time; both frontends emit.
- Drove the built apps in Chromium against the live API and seeded data:
  guest marketplace renders with `200 /settings/public` and
  `200 /products?featuredOnly=true`; `PTG-100001` signs in (`201 /auth/login`)
  and lands on `/app` with the partner nav; `PTG-ADMIN` signs in and lands on
  the admin console. No console errors beyond the expected anonymous `401`
  on `/auth/refresh`.

Then re-verified in **dev mode**, which is what was broken, by driving a real
Chromium at `pnpm dev`:

- web boots at `:5173`, 13 `.ts` modules served `200`, guest marketplace
  renders in Arabic, `PTG-100001` signs in and lands on `/app`
- admin boots at `:5174`, `PTG-ADMIN` signs in (`201 /auth/login`), lands on
  the dashboard with real figures (`200 /admin/dashboard` — 12 users, 6
  partners, $49.98 revenue)
- no failed requests in either app; the only console noise is the expected
  anonymous `401 /auth/refresh` and a recharts `defaultProps` deprecation
  warning from `XAxis` (upstream, React 18.3, cosmetic)

## Open questions / follow-ups

- The IDM driver is per-machine. Anyone else who runs this repo on Windows
  with IDM installed will hit exactly the same blank page, and the fix needs
  an elevated shell.
- Whether IDM's own *Options → File Types* dialog would have fixed it without
  touching the driver is untested — the registry-level equivalent did not.
- `apps/admin`'s main chunk is 920 kB (`index-*.js`) and warns on every
  build. Only `vendor`/`query`/`charts` are split out; the pages are lazy
  but the shared feature code is not.
- `recharts`, `zod` and `@hookform/resolvers` are declared as dependencies of
  apps that never import them (recharts in web; zod/resolvers in admin).
  Harmless, but they inflate the install.
- `@ptg/ui` still resolves to `src/index.ts`, unlike types/config which now
  ship built output. It works because only bundlers consume it, but it is an
  inconsistency worth deciding on deliberately.
