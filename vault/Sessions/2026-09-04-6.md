# 2026-09-04 (6)

Put both sites on the Oracle Cloud box — PTG and AradoBot — and built the
one-command update path from Windows for each. Six latent bugs had to be
fixed on the way: one would have made sign-in fail on any non-HTTPS
deployment, one meant PTG's images had never successfully built, and one meant
AradoBot's `main` could not be compiled at all.

## Did

### Found out what the server actually is

Nothing in the repo or vault recorded the target. The IP came from
`~/.ssh/known_hosts` (`130.110.124.121`, matching the `ssh-key-2026-08-21.key`
sitting untracked in the repo root — Oracle Cloud's default download name).
`ubuntu@` was refused; the box is Oracle Linux, so the user is `opc`.

What it is, and every bit of it constrained the design:

- Oracle Linux Server 9.8, **aarch64**, 2 vCPU, 10.9 GB RAM, 183 GB disk.
- **Rootless podman 5.8.2**, not Docker. `docker` on `$PATH` is podman's CLI
  emulation; `docker compose` shells out to `podman-compose` 1.6.0.
- Not empty: another project, `pricelens`, was running five containers on
  ports 3000 and 3001. Stopped it on request — `podman stop` only, its files
  and volumes are untouched, and it can be brought back with
  `podman start pricelens_postgres_1 …`.
- `firewalld` allowed only ssh, 3000 and 4000. Measured from outside once
  something was listening: `:3000` answers, `:4000` refuses the connection
  (the packet reaches the host), `:80` *times out* — dropped by the OCI VCN
  security list before it ever arrives. That list is edited in the Oracle
  console, not on the box, so **3000 and 4000 are the only ports there are**.

### Host setup (recorded in [DEPLOYMENT.md](../../docs/DEPLOYMENT.md))

- `firewall-cmd --permanent --add-port=80/tcp`
- `net.ipv4.ip_unprivileged_port_start=80` in
  `/etc/sysctl.d/99-ptg-unprivileged-ports.conf` — without it rootless podman
  cannot bind :80 at all.
- `loginctl enable-linger opc`, plus `podman-restart.service` enabled by the
  deploy script, so the stack survives a reboot. It previously did not:
  `pricelens` had no systemd units and linger was off, so a reboot would have
  taken that site down silently.

### The deployment

- `docker-compose.server.yml` — self-contained single-VM stack.
- `infra/nginx/server-proxy.conf` — one origin on :80 and :3000: web at `/`,
  admin at `/admin/`, API + `/health` + `/docs` + `/media/` alongside.
- `deploy/remote-sync.sh` (piped over stdin, so it works on a box with no
  checkout yet) and `deploy/server-update.sh` (build → migrate → seed if the
  users table is empty → restart → health-check).
- `update-server.bat` — the single command. Reasoning in
  [[../Decisions/0008-single-vm-podman-deployment]].
- `deploy/server.env` holds production config and is uploaded as the server's
  `.env` **every run**, so there is no server-side file to drift.
  Gitignored; `deploy/server.env.example` is the committed template.

### Two bugs the deployment forced out

**`z.coerce.boolean()` inverted every `false`.** `COOKIE_SECURE=false` parsed
to `true`, because `z.coerce.boolean()` is `Boolean(value)` and every
non-empty string is truthy. A `Secure` cookie over plain HTTP is dropped by
the browser with no error anywhere — sign-in would have failed on the server
with nothing to go on. `DEMO_MODE` and `S3_FORCE_PATH_STYLE` had it too. See
[[../Decisions/0009-env-booleans-are-parsed-not-coerced]].

**`prisma/seed.ts` could not run in the built image.** It imports the
placement-path helper from `../src/`, and the API runtime stage copied only
`dist/` and `prisma/`. Half a megabyte of TypeScript now comes along.

### Two that showed up during the deploy itself

- `deploy/server-update.sh` originally did `. ./.env` to read
  `POSTGRES_USER`. That treats a compose env_file as a shell script, and
  `VITE_BRAND_NAME=PTG Business` aborted the run with
  `Business: command not found`. It reads individual values with `sed` now.
- `.gitattributes` pins `*.sh` to LF. `core.autocrlf` is true on this
  checkout, so without it every deploy script would reach the server with
  carriage returns and fail in bash.

### Then AradoBot went on the same box

Same server, second app: Next.js web + Express API + MongoDB Atlas Local,
running under pm2 rather than in containers (node 20, pnpm 10.34.3 and pm2
were already installed — the box had been prepared for it, but nothing was
deployed: no checkout, no pm2 processes).

Two ports for two apps meant PTG had to give up 4000 and fold its admin
console under `/admin/` on 3000 — see the amendment on
[[../Decisions/0008-single-vm-podman-deployment]].

- `~/aradobot` cloned from `Digital-Fingers-Team/bookbot`, `.env` uploaded and
  rewritten for the box: `PORT=4001`, everything public pointed at `:4000`,
  `TRUST_PROXY_HOPS=1`.
- Both processes bind loopback only (API 4001, Next 3001); an nginx container
  on the host network owns `:4000` and splits by path. The API's routes are
  all under `/api/*` already, so nothing needed rewriting.
- Mongo indexes, the default admin and default categories are all created by
  the API at boot — that is AradoBot's "migration", and it ran.
- The Atlas **vector search index did not exist and nothing in the code
  creates it** (`check-vector-index.ts` only checks). Without it retrieval
  answers 503. Created by hand on `chunks`: 1536-dim cosine on `embedding`
  plus a `bookId` filter field; status READY.
- `pm2 save` + `pm2 startup` (systemd unit `pm2-opc.service`), so it comes
  back after a reboot.

### Four things that had to be fixed to get either app up

**PTG's images had never built.** `docker-compose.prod.yml` was untested: no
Dockerfile copied the repo-root `scripts/` that `@ptg/types`/`@ptg/config`
shell out to, and web/admin built their app *without* building those packages
first — so every `@ptg/types` import failed `TS2307` and cascaded into ~30
implicit-any errors.

**Container DNS was dead for every network.** `prisma migrate deploy` failed
with `getaddrinfo EAI_AGAIN`. Rootless podman runs one `aardvark-dns` for all
of a user's networks, and each file in its runtime directory names a gateway
it must bind. A stale `aradobot_default` entry named `10.89.0.1` while the
network had been recreated on `10.89.2.1`; aardvark could not bind an address
that no longer existed, exited, and took DNS down for *every* network —
including PTG's, which would equally have stopped the API resolving
`postgres`. Deleting the stale entry fixed it, and `deploy/server-update.sh`
now prunes entries for networks with no running containers before starting.

**AradoBot's `main` did not compile.** `toPublicUser` became `async` in the
org-admin access change but kept a bare `PublicUser` return annotation —
`TS1064`, so `pnpm build` fails and no deploy of that branch could ever have
worked. This account has no push access to `Digital-Fingers-Team/bookbot`, so
it is carried as `deploy-patches/0001-topublicuser-promise.patch`, re-applied
after each hard reset. **It should be pushed upstream and the patch deleted.**

**`podman-restart.service` resurrected `pricelens`.** Enabling it so PTG
survives a reboot also restarted every container with
`restart: unless-stopped`, which included the pricelens containers that were
supposed to stay down. Fixed with `podman update --restart=no` on each of
them — the containers, volumes and files are all still there.

### Then the site was opened in a browser, and none of it worked

Every page rendered its shell and then showed "Something went wrong. Please
try again." Three separate bugs, each of which alone was enough.

**`new URL()` throws on a relative base.** `apps/web/src/lib/api-client.ts`
built request URLs with ``new URL(`${BASE_URL}${path}`)``. The server build
sets `VITE_API_URL=/api/v1` (the API is same-origin behind the proxy), and
`new URL()` rejects a relative string when given no base - so *every* request
threw a `TypeError` before `fetch` was reached. Dev never saw it because the
fallback, `http://localhost:3001/api/v1`, is absolute, and every existing spec
ran on that fallback. `apps/admin` had the identical line. Both now pass
`window.location.origin` as the base, which is ignored when the first argument
is already absolute. `api-client.spec.ts` has a case that pins the relative
build and fails with the real `Invalid URL: /api/v1/products` without the fix.

**The deploy had never actually shipped a frontend.** `podman-compose`, unlike
docker compose, leaves a running container alone when the image it was built
from has been replaced. `compose build && compose up -d` therefore produced
new images that nothing ran, and reported success while serving the previous
bundle - confirmed by the asset hash on the live page not moving across a
deploy. `compose up -d --force-recreate api web admin proxy` now, with the
stateful services left alone.

**`location /health` ate the Health section.** nginx prefix-matches, so the
API's infra probe took `/health`, `/health/management`,
`/health/knowledge/...` - the entire Health feature returned JSON on any
reload or shared link, while client-side navigation between them worked fine
and hid it. The API's own comment says the probes are mounted outside
`/api/v1` "so they never collide with the product's own `/health/*` feature
routes", which is true per-app and false on a shared origin. Probes moved to
exact-match `/healthz{,/live,/ready}`; the deploy healthcheck execs into the
container and never used the proxy anyway.

## Decided

- [[../Decisions/0008-single-vm-podman-deployment]] — self-contained compose
  file, PTG on one origin with the admin console under `/admin/`, AradoBot on
  the other port, env uploaded every run.
- [[../Decisions/0009-env-booleans-are-parsed-not-coerced]] — no
  `z.coerce.boolean()` on anything from `process.env`.

## Open questions / follow-ups

- **Nothing here was verified in a browser until the user opened one.** Every
  check was `curl` against endpoints, which cannot catch a client-side
  `TypeError` in URL construction, an SPA route shadowed by a proxy prefix, or
  a stale bundle being served. A smoke check that loads a page and asserts the
  product list actually renders would have caught all three.
- **Port 80 is blocked by OCI**, confirmed by measurement. Adding an 80
  ingress rule in the Oracle console would let PTG serve from the bare IP with
  no other change (the proxy already binds it) and would free `/admin/` to go
  back to its own origin if wanted.
- **The AradoBot compile fix needs to reach upstream.** Until someone with
  write access to `Digital-Fingers-Team/bookbot` merges it, every deploy
  depends on a local patch file that lives only on this machine.
- **`tesseract.js`'s build script was skipped** by pnpm during the AradoBot
  install (`Ignored build scripts: tesseract.js@7.0.0`). That is the *local*
  OCR fallback; cloud OCR via OpenRouter is unaffected. Worth confirming
  before relying on offline OCR.
- **AradoBot's OMP push is switched off** (`OMP_PUSH_ENABLED=false`), because
  `OMP_BASE_URL` points at `localhost:8091` and OMP is not deployed on this
  box. Turn it back on when it is.
- **Two apps now share 2 vCPUs.** AradoBot runs OCR and embedding work at
  `OCR_CONCURRENCY=4` / `PROCESSING_CONCURRENCY=3` (the values its own deploy
  script chose for this box, from when it had the box to itself). Worth
  watching under real ingestion load.
- **No TLS, no domain.** Everything is `http://` against a bare IP, which is
  why `COOKIE_SECURE=false` and `COOKIE_DOMAIN=` (empty — a cookie whose
  `Domain` is an IP address is rejected by every browser). Both need
  revisiting the moment a domain exists.
- **`pricelens` is stopped, not removed**, and it will not come back on its
  own. If it is meant to keep running, it needs its ports moved off 3000 and
  a decision about which project owns :80.
- The seeded demo accounts (`PTG-ADMIN`, `PTG-100001`, `PTG-C0001`, password
  `Passw0rd!Demo`) are live on a public IP. Fine for a demo, not for real
  data.
